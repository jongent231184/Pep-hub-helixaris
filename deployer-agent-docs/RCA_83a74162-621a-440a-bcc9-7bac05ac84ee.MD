# RCA — GHP Health (www.ghp-health.com) "data loss" after fork republish

## Summary (good news first)
**No data was deleted. Nothing was overwritten.** The live site is simply pointed at the **wrong MongoDB**. The original GHP production database is fully intact and still holds every product (with variants) and all 1896 orders. Restoration = re-point the deployment back to the original DB + merge 2 new orders placed after the swap.

## 1) Which deployment / job / DB serves www.ghp-health.com

- **Deployment:** `ghp-ecommerce-pay` (deployment_id `eed29dfe-b11a-432c-8a6e-3887ebf174df`). Both `ghp-health.com` and `www.ghp-health.com` are verified domains on it.
- **Active run (currently live):** `83a74162-621a-440a-bcc9-7bac05ac84ee`
  - type = **`replacement`**
  - job_id = **`411a925d-b8bf-4a9f-a781-1caf3e06605d`** ← the **forked** job
  - created 2026-10-20 **08:37:14Z**, completed **08:44:05Z**
- **All prior runs** on this deployment belong to a DIFFERENT job: job_id **`ca026de8-11aa-4118-9315-cde24f5755d7`** (the original GHP job).

### The DB binding changed
| Run | Job | DB it is bound to |
|---|---|---|
| Active `83a74162` (fork replacement) | `411a925d` (fork) | **`dual-brand-store-test_database`** |
| Previous `cfe67463` (original GHP) | `ca026de8` (original) | **`ghp-ecommerce-pay-test_database`** |

The fork's **replace** publish re-bound the live deployment's `MONGO_URL` from the original DB (`ghp-ecommerce-pay-test_database`) to the fork's own DB (`dual-brand-store-test_database`). The replace does an atomic swap of the whole app (including its DB binding) — it did **not** migrate or overwrite the original DB.

## 2) Does the previous production DB still exist? — YES, intact

Verified read-only against the original DB `ghp-ecommerce-pay-test_database` (via run `cfe67463`):
- **orders: 1896** docs; latest `GHP-1921` at **2026-10-20 08:23:08Z** (the last real order before the 08:37 swap).
- **counters.seq = 1921** (matches GHP-1921).
- **products: 66**, with real, varied prices and real `updated_at` timestamps (e.g. "BPC 157 10mg" £30 updated 2026-09-28; "MT-2 10mg Nasal" £25 updated 2026-08-11) — i.e. the genuine catalogue with variant data.

Current (wrong) DB `dual-brand-store-test_database` (via active run `83a74162`):
- **orders: 45** (`GHP-001`…`GHP-055`); **counters.seq = 55** — a preview-snapshot sequence, not production.
- products uniformly £37.50 with empty `variants: []` — this matches the fork's preview seed, exactly the symptom the user saw.

No Atlas snapshot/backup is required — the real production DB is live and complete.

## 3) How to restore WITHOUT losing the 2 new real orders

Two real orders were placed into the WRONG DB (`dual-brand-store-test_database`) during the window the site was mis-pointed (customer: Clare Ballinger, clare.ballinger@gmail.com):
- **GHP-054** — created 2026-10-20 **10:00:13Z** — 1× "T1RZ3P4T1D3 30mg" £37.50, total £42.49. `payment_status: failed` (wallid FAILED).
- **GHP-055** — created 2026-10-20 **10:04:33Z** — 1× "T1RZ3P4T1D3 30mg" £37.50 + 1× "BAC WATER" £2.50, total £44.99. `payment_status: pending` (wallid NEW).
(Both are incomplete/unpaid payment attempts, but should be preserved for reconciliation.)

### Recommended restore sequence (do NOT wipe either database)
1. **Keep the deployment private** (already done) so no further writes land in the wrong DB.
2. **Platform re-point:** Emergent re-binds deployment `ghp-ecommerce-pay`'s `MONGO_URL` back to **`ghp-ecommerce-pay-test_database`**. `MONGO_URL` is a platform-managed SYSTEM secret and the binding was set by the replace deploy — it cannot be changed from the Secrets tab or by a normal redeploy (a redeploy would re-apply the current, wrong binding). This instantly restores all products+variants and all 1896 orders.
3. **Merge the 2 new orders** GHP-054 & GHP-055 into the original DB (full documents captured above), setting their order numbers to continue the real sequence (next would be GHP-1922, GHP-1923) and bumping `counters.seq` accordingly — or retain their numbers if you prefer, but avoid collision with the 1921 sequence.
4. **Preserve, do not delete** `dual-brand-store-test_database` until the merge is confirmed — it is the only copy of GHP-054/055.
5. Re-publish/verify, then set the deployment public again.

### Critical warnings
- **Do NOT trigger any redeploy or re-publish of `ghp-ecommerce-pay` (or re-run the fork job `411a925d`) before the binding is corrected** — the current production state points at the wrong DB, so a redeploy will re-apply the wrong `MONGO_URL`.
- Do not use the fork job to "replace" this deployment again.
- The separate **Helixaris** deployment (helixaris.com) is a different deployment/DB and is unaffected.

## Root cause (one line)
The fork job `411a925d` published a **replace** against the live GHP deployment on 2026-10-20 08:37Z, which atomically swapped the app AND its database binding to the fork's preview DB `dual-brand-store-test_database`; the real production DB `ghp-ecommerce-pay-test_database` was never touched and is fully intact.
