## 3) Why the republish (and the rollback) did NOT fix it
MONGO_URL and DB_NAME are **SYSTEM** secrets. They are regenerated from the deployment's **production state** on EVERY deploy and always overwrite any other value; they are never settable from the Secrets tab.

The deployment's production-state DB binding was corrupted earlier by the fork's **replacement** run `83a74162` (job 411a925d, 2026-10-20T08:37), which bound the ghp-ecommerce-pay deployment record to `dual-brand-store-test_database`. From that point every subsequent run just regenerates the same wrong system secrets from that stored state:
- rollback `2b13643b` (job ca026de8, 11:04) → reused an old image AND carried the corrupted MONGO_URL/DB_NAME forward.
- redeploy/republish `9b4ea695` (job ca026de8, 11:12, now active) → "Replace/Republish" regenerated system secrets from the SAME corrupted production state, so it re-applied `dual-brand-store-test_database` again.

So the user's hypothesis is correct: **the republish carried over the current (corrupted) system secrets.** Rollback, redeploy, and replace cannot fix this because they all read the wrong binding from production state — and a Secrets-tab edit of DB_NAME/MONGO_URL would be overwritten on the next deploy.
